# Design decisions

Append new decisions at the bottom. When a decision is replaced, keep the old entry and mark it "Superseded by ...". Entries dated 2026-09-22 come from older notes without an exact date; those decisions were made on or before that day.

### 2026-06-14 New capabilities extend the existing API

A new capability becomes an optional field on the API everyone already calls, not a second factory or function next to it. A parallel "opt-in" surface never gets adopted, so old call sites stay behind and the code collects near-duplicates. The case that settled it: a fourth config factory for boot configuration was dropped, and `env`, `inheritedToTenant` and `backing` became optional fields on `ConfigKeyOptions`, inherited by the three scope factories. A new surface is only justified when the semantics are truly disjoint.

### 2026-08-19 PII encryption happens only in `append()`

Ciphertext in tables such as the job-run and delivery-attempt stores comes from `crypto/event-pii.ts`, called from the event store's `append()` and driven by the `piiFields` catalog of `r.defineEvent`. Columns and tables know nothing about PII, so any write path that bypasses `append()` stores plaintext without an error. A direct write has to call `encryptPiiValueForSubject` itself. Extending the catalog at runtime does not work, because `configureEventPiiCatalog` replaces it and runs once at boot with the state of all features. Without a configured KMS the result is plaintext by design (documented fail-open), because some apps boot without one. Introduced with fw#2243.

### 2026-08-20 List limits are capped at 200, callers page with a cursor

`MAX_LIST_LIMIT = 200` bounds `entityListSchema.limit` and is clamped again in `resolveListPagination`. It was added as a security fix against unbounded or fractional `LIMIT` in raw SQL (first in 0.201.0, clamp in 0.203.0). A caller that needs a complete set pages through `nextCursor` until it is empty. Lowering the requested limit silently drops rows and is not a fix. The constant is exported from the engine entry, but importing it as a value into client code breaks the browser build, so views use a literal.

### 2026-09-09 Authenticator enrolment and personal access tokens stay custom screens

`auth-mfa` enrolment and `personal-access-tokens` keep `type: "custom"` screens (framework#2312). Both show a secret exactly once (TOTP secret and recovery codes, token plaintext) straight from the write response. The declarative form handler discards everything except the created id, so showing the value declaratively would mean reloading it through a cacheable query, which is the real security defect. Building a write-response display into the framework was rejected as out of scope. Both are deliberate exceptions to the custom-screen migration.

### 2026-09-09 Custom screens are fine when they follow the standard

A screen that is genuinely custom (a gallery, an ad-hoc comparison) may stay custom. It has to use the framework widgets and layout conventions instead of rebuilding cards, forms and button rows by hand. Action buttons belong in the card's `footer` slot, not loose in the body. The `ui-guards` and `primitives-discipline-guard` checks do not cover this (framework#2680), so review has to.

### 2026-09-22 `pii: true` is for crypto-shredding, `encrypted: true` is for secrets

`pii: true` with a subject marker encrypts through the subject KMS so that destroying the subject key makes the ciphertext unreadable. It is transparent to the application: the executor encrypts on write, decrypts on read, and handlers see plaintext. `encrypted: true` goes through the field cipher and is for secrets that must be read back, such as an SMTP password or an external API key. GDPR does not require field encryption. Nothing about access, search, sort or display may be restricted just because a field is `pii: true`.

### 2026-09-22 Event sourcing means no relational pivots

Cross-aggregate views are composed in the read layer from several projections, never with a SQL join over a pivot table. A generic "applies to any entity" feature such as tagging uses a feature-owned projection keyed on `(entityType, entityId)` and merges in the read layer, so it works for every host entity without touching it. Denormalizing a column onto the host entity (the `custom-fields` pattern) is the alternative when the host can declare it. Entity ids are uuid or text, never numbers.

### 2026-09-22 Entity index changes live in `entity.indexes`

`buildEntityTable` derives every unique and composite index from `entity.indexes` each time the table is built, so the migration file is not the source of truth. A hand-written `DROP INDEX` or `CREATE UNIQUE INDEX` disappears at the next destructive projection change and shows up as drift in `kumiko-schema validate`. An index that needs to change is changed in the entity definition. The email index on `user` is global on purpose because the user aggregate is tenant-agnostic, so a per-tenant composite would let one address resolve twice.

### 2026-09-22 Cookie domain widening forbids authenticated writes from tenant subdomains

When `auth.cookieDomain` widens the session cookie across subdomains, the framework requires a static `auth.allowedOrigins` list without wildcards and refuses to boot otherwise (`assertOriginGuardConfig`). A subdomain XSS could read the wide cookie. The consequence for app design is that tenant subdomains can only serve anonymous, read-only content. Authenticated writes belong on one fixed host. `unsafeSkipOriginCheck` with a replacement CSRF defence exists but is a security downgrade and not recommended.

### 2026-09-22 Client screens import from a client-safe `/web` entry

A bundled feature's main index re-exports entity, handlers and executor, which pull `postgres` and Node builtins into the dependency graph. A client screen importing from it fails `bun build --target browser`, and tree-shaking does not reliably save it because of module-level side effects. Every feature with a client surface therefore exposes `<feature>/web/index.ts` (marker `// @runtime client`, own `exports` entry) that re-exports only qualified names, pure helpers, types and components. If the entry is missing it is added to the framework first, not duplicated in the consumer.

### 2026-09-22 One anonymous route uses a path gate, not a second bundle

For a single anonymous route inside an existing SPA, a path gate placed as a client feature gate before the email-password client is enough. It follows the existing `AuthPathGate` pattern and has no session context. `createPublicSurface` (separate entry bundle, host routing, server wiring) is for whole public sites. A new public path must also be reachable through the production host dispatch, so the prod entry point is checked, not only the dev one. Pages rendered inside marketing chrome must not use `<header>` for titles or the sticky title bar of the `Form` primitive, because both collide with the sticky site header.

### 2026-09-22 No guardrails against self-inflicted misuse

Docs, recipes or checks that exist only to stop an app author from doing something that harms nobody but themselves (an untidy settings hub from many one-key features, verbose code, redundant features) are not built. Preventive tooling is reserved for data loss, security and cross-tenant harm.

### 2026-09-25 Dependency outages degrade and recover instead of crashing

When a dependency such as Postgres goes away, the process stays up. It reconnects with backoff and an upper bound, never gives up after N attempts, logs distinct `lost, reconnecting` and `recovered` lines, reports readiness as not ready while liveness stays green, and resumes without a restart. A hard exit is for real programming errors. Crash loops turn a short outage into restarts of every pod with Kubernetes backoff delays of up to five minutes (framework#3243).

### 2026-10-20 Event-fed tables are write-locked at runtime

Tables built by `buildEntityTable` or registered through `r.projection` carry a runtime mark, and every write path (the query helpers, the `ctx.db` methods and `db.global()`) refuses them unless the runner holds a capability that only the framework hands out. It goes to the executor, projection apply and rebuild, declared `unsafeProjection*` steps, tenant-destroy hooks for their own tenant and `deleteRowsWithoutReplayableStream`, which deletes only rows whose stream has no events or is archived. `unsafeRaw()` strips it, so an audited escape hatch still cannot write a read model without an event. The capability sits on a per-grant runner proxy and never on the shared pool or transaction. The compile-time half is a positive brand: a write compiles only for a `Writable` table (`table()`, `defineUnmanagedTable`, `source: "unmanaged"`) or a runner that carries the capability type, and widening a table to a plain schema table drops the brand, so erasure fails closed. The direct-entity-writes guard remains as early warning and for raw SQL. A static guard alone missed casts and type-erased tables, and every miss was a row that a rebuild drops or resurrects.

### 2026-10-20 Feature runtime follows the path

Inside a feature, `web/**` is client-safe code and everything else is server or isomorphic, so the runtime-isolation guard derives the runtime from the path and the `// @runtime client` marker is gone from feature folders. Isomorphic `constants.ts` and `i18n.ts` live under `web/` and the server imports them directly; there is no separate `shared/` folder. Markers remain only outside feature folders (dev, test and tooling files without a path rule). The `feature-layout` codemod moves existing files and `guard-app-feature-structure` flags new markers.

### 2026-10-20 Error classes are closed by types, boot or runtime before a guard

When a guard finds an error class that a type, the boot validator or a runtime check can make impossible, the framework closes it there and the guard goes. A guard stays only where the check needs cross-file context the framework cannot see, or where an export still has legitimate cross-package users (admin-api, restricted-symbols, raw-sql). Placeholder reasons ("todo", "legacy", ...) are rejected at boot for every declared `escapeHatch` and `openToAll`, and at runtime for call-site reasons (`unsafeRaw(reason)`, `acknowledgeCrossTenant`, `unsafeAllTenants`, `declareEscapeHatch`). The accepted trade-off: a new placeholder at a call site that rarely runs surfaces only when that path executes, not in CI. Undeclared `unsafeRaw` or SYSTEM-identity use was already refused at runtime and is no longer flagged statically.

### 2026-10-21 Second guard sweep: runtime, boot and contract tests

The unsafe-append-event guard goes without a replacement, because the event store already rejects unregistered event types and validates every payload at runtime for `appendEvent` and `unsafeAppendEvent` alike. The access-denied-test guard is replaced by the `expectRoleRestrictedHandlersDenyForeignRole` contract helper, which calls every role-restricted write and query handler over HTTP, since roles are enforced centrally before parsing. Locale completeness moves from the i18n-keys guard to the boot validator as a per-feature consistency check: every key carries every locale its feature uses. The PII stance of entity text fields is deterministic: `FieldsMap` requires one by type and boot refuses a text or long-text field without one, while the name heuristic stays a warning and never fails. The qualified-name guard and the i18n used-key-without-definition check stay, because making them type errors would need code generation.

### 2026-10-21 The primitives contract stays, files stay under 2000 lines

`usePrimitives` and `PrimitivesProvider` remain the public seam between screens and their building blocks. Apps override single primitives through it and tests swap them without a DOM, so removing it would break every consumer for no gain. Its docs no longer mention renderer packages that do not exist. Production files in the framework packages stay under 2000 lines, enforced by the file-size guard with a baseline; translation tables (`locale-*/src/strings.ts`) and tests are exempt. Legitimate bridge and boundary casts are counted per package in a second cast baseline, so moving code between files does not trip it while new casts do. Tenant-bound newest-row-per-key reads use `selectMany` with `distinctOn` instead of `unsafeRaw`; a generic custom-SQL read on `TenantDb` was rejected, because the framework cannot prove the tenant filter inside arbitrary SQL without row-level security.

### 2026-10-21 Required locales are an app boot option

An app names the locales it ships in `validateBootOptions.requiredLocales`, and boot fails on any translation key of any mounted feature, framework and bundled ones included, that lacks one of them. The list is not derived from tenant settings: those change at runtime, while the check has to hold for one build in CI (`kumiko-schema validate` reads the same option). Locales are combined across features, so a `locale-*` package closes the gaps of the features it translates; a plain key of a regular feature only counts for that feature, so two features with the same plain key cannot cover each other. Generated labels that only exist in English, such as personal-access-token scopes, get a key helper (`patScopeOptionKey`) instead of a localized `label`, because locales on the defining feature would make every one of its keys need all of them under the per-feature consistency rule.

### 2026-10-21 Cross-tenant reads are a per-handler read-only grant

A tenant-scoped handler or job that only has to read other tenants' rows declares `escapeHatch: { reason, grants: ["crossTenantReads"] }` and gets `ctx.crossTenantReads` (`selectMany`, `fetchOne`, `count`, each call counted in the escape-hatch metric, audited as `cross-tenant-read` once per report window). The grant does not unlock `ctx.db.unsafeRaw()`, writes or `db.global` writes, and neither member-resolution reads nor agent tool calls ever see it: `dispatchToolCall` marks its scope, nested dispatches inherit the marker, and the check also covers a grant implied by `unsafeRaw`. `unsafeRaw` implies it, because the raw runner reads everything anyway, so existing declarations keep working. Lifting the feature to `r.systemScope()` or moving the handlers into a separate system feature was rejected: it widens the scope to every handler of the feature or renames qualified names. The agent check sits in the dispatch rather than in agent exposure, because exposure only decides which handlers an agent may call, while the call itself runs with the user's session and its result lands in the LLM context.

### 2026-10-21 Public packages are MIT, not BUSL-1.1

BUSL-1.1 was chosen in 2026-05 to keep a large vendor from forking the framework into a hosted offering without giving anything back. The review on 2026-10-21 showed the trade-off no longer holds: a framework with one maintainer gains more from adoption and contributors than it loses to a hypothetical fork, BUSL is a sticking point in dependency scans (the own license guard denies it), and the Additional Use Grant forced every hosting question into a mail thread. All `@cosmicdrift/*` packages, `create-kumiko-app` and the repo switch to MIT; the dependency-license exceptions for BUSL stay, because every version up to 0.386.0 was published under it and a consumer may still pin one. Contributions come in under MIT with a DCO sign-off instead of a CLA, so the copyright stays with the contributors and a later relicensing would again need everyone's consent.

### 2026-10-22 Complexity cap 60, files under 1200 lines, projection allowlist at boot

A function above cyclomatic complexity 60 fails the complexity guard in the repo's own files, even with a complexity-budget tag or a baseline entry. The tag and the per-file baseline only cover the range from 15 to 60. Production files stay under 1200 lines, frozen by the file-size baseline as before; this replaces the 2000-line limit from 2026-10-21. `validateBoot` runs `validateProjectionAllowlist`, so a write handler that writes a projection it did not declare, or writes an aggregate table directly, fails at boot instead of passing silently. Aggregate tables are matched by their physical table name.

### 2026-10-22 Billing offers several providers for new checkouts only

`billing-foundation` serves the plan catalog from every mounted provider that exposes `priceToTier` and offers those the system admin has switched live. The customer picks one in the order dialog after choosing a plan. A subscription stays with the provider stored on it for prices, plan switch, portal, cancellation and sync, and a switch never crosses providers, because the provider subscription id only exists at that provider. A provider without a hosted switch page (Dodo Payments) switches plans through a preview in the app and the same consent gate as a checkout, so a plan change never happens without the customer seeing the amount and consenting. Dodo's test or live environment is its own config key next to `billingLive`, so staging can run real test checkouts with billing switched on. The Dodo-specific parts are superseded by the entry of 2026-10-26.

### 2026-10-22 List groups and totals are computed on the server

A grouped list or a totals row shows numbers over the whole filtered result set, never over the rows a page or an infinite scroll has loaded so far. With client-side grouping a group would show only the rows of one page and grow while scrolling, a collapsed group would still load silently, and sums would be page sums that change as the user scrolls. The `list` query therefore takes an optional `aggregate` payload (one `groupBy` field plus `sum`, `avg`, `count`, `min` and `max` measures) that runs over the same where clause as the rows, including ownership, screen filters and the Meilisearch candidate ids, through the existing `aggregate-sql.ts` layer and the same field-read gate as sorting and filtering. The renderer loads groups first and then rows per expanded group with its own cursor, so pages and infinite scroll behave the same in group mode. Table view state (columns, pins, widths, density, grouping) lives in the browser session behind a `ListStateStore` keyed by tenant, user and screen; the URL stays the source of truth for sort, search, page and filters, and nothing about a table view is persisted on the server. Bulk actions call the existing row write handler once per row instead of `/api/batch`, because the batch is atomic and a single rejected row would roll back every other one.

### 2026-10-22 Complexity cap 40

The hard complexity cap drops from 60 to 40 and replaces the cap of 60 from the entry of the same day above. A function above cyclomatic complexity 40 fails the complexity guard in the repo's own files, even with a complexity-budget tag or a baseline entry; the tag and the per-file baseline only cover the range from 15 to 40. The functions that sat between 40 and 60 were dispatch over a closed set of kinds (PII rules, cascade strategies, list columns, cell formats), and a typed table of small rules expresses that with every rule under 30. The thin-wrapper guard therefore no longer reports a function that fills a slot of a typed table (an object literal with a declared type or a `satisfies` check): the table fixes the signature, so inlining the entry would mean dropping the table.

### 2026-10-23 Bun.SQL is the only Postgres driver

Bun.SQL replaces the postgres-js fork (`@bender0oo0/postgres`) behind `createDbConnection`, and the fork leaves the workspace. The only thing that held Bun.SQL back was oven-sh/bun#29484: a prepared statement kept its plan across DDL on the same connection and failed with 0A000, which broke projection rebuilds and column DDL. Bun 1.4.4 fixes it, so the framework requires Bun 1.4.4 or newer and a regression test runs exactly that sequence on one reserved connection. With one driver there is one error shape: the SQLSTATE comes from `errno` and the constraint from `constraint`, read only through `extractPgError`, and connection failures carry Bun's `ERR_POSTGRES_*` codes. `DB_PROVIDER` is refused at boot for every non-empty value, because there is nothing left to select. `onNotice` is gone without a replacement, since Bun.SQL has no notice hook and drops server notices. Keeping postgres-js as a second driver was rejected: two drivers double the parity work on array parameters, instants and savepoint errors that PR #3767 had to do once, and no app imports postgres-js directly.

### 2026-10-23 ts-morph tooling lives in its own package, @cosmicdrift/kumiko-feature-ast

The feature AST (parse, patch, render), the pattern library, the codemod pipeline and the upgrade codemods moved out of `@cosmicdrift/kumiko-framework` into `@cosmicdrift/kumiko-feature-ast`; the framework no longer depends on it and no longer installs ts-morph. They are a library for runtime consumers (the studio designer, the enterprise `ai-generate` feature, the dev server), not a CLI, so a place inside `@cosmicdrift/kumiko-cli` was rejected: the CLI already depends on the dev server, which would close a cycle. Production images that install only the framework drop ts-morph and the TypeScript compiler it bundles. The upgrade codemods keep the `scripts/codemod/` subfolder, so the `codemod` paths in every `changes.json` stay valid, and `kumiko-upgrade` and `kumiko codemod` look for them in this package.

### 2026-10-23 Optional peers fail at the subpath, not at boot

A subpath that needs an optional peer dependency fails on import with `<peer> is not installed. <subpath> needs it as a peer dependency: bun add <peer>@<range>` and is listed in the package's `kumiko.optionalPeerExports`. The framework itself boots without the peer; the first case is `meilisearch` for `@cosmicdrift/kumiko-framework/search/meilisearch`. Only the peer's own "package not found" error is translated, so a missing dependency of the peer still surfaces unchanged. check:dist does not install the peer and checks exactly that message under Node and Bun, and the hero demo refuses to run when meilisearch ended up in the scaffolded app.

### 2026-10-23 Row level security is a second isolation layer, on by default

Postgres row level security sits under the tenant filter of TenantDb as a second layer and does not replace it. With `rowLevelSecurity: "on"` every table with a `tenant_id` column, the event store tables included, gets ENABLE and FORCE ROW LEVEL SECURITY and the policies `kumiko_tenant_isolation` and `kumiko_system_tenant_read`, and the connection sets `kumiko.tenant_id` and `kumiko.scope` transaction-locally in every transaction from an ambient scope. TenantDb and dispatch set the tenant; jobs, the event dispatcher, member resolution, migrations, seeds, rebuilds and the other boot paths set the system scope at the call site. A statement without a scope sees no tenant rows. The functions that set a scope are not on the public `db` subpath: the framework packages import them from `internal/row-level-security` and tests from `@cosmicdrift/kumiko-testing/helpers`. The guard `internal-subpath-imports` keeps code outside the framework repo off `internal/*`, keeps the setters from `testing/helpers` in test files and requires a literal reason at every system scope entry, so each cross-tenant path names why it needs one. One value in `kumiko.config.ts` drives schema generate, validate and apply and every runner, so the CLI has no flag of its own that could disagree with the runtime. The default is on everywhere, production included; `"off"` stays as an explicit opt-out and logs a boot warning. The test stack and the dev server run as a NOSUPERUSER NOBYPASSRLS role that owns the database; the production roles were checked before the flip (all app roles NOSUPERUSER NOBYPASSRLS, each owning its database). At on, boot refuses a role with SUPERUSER or BYPASSRLS and any tenant table without the full set; at off, it refuses a database that still has row level security enabled. Projection rebuilds run under FORCE in system scope instead of turning `row_security` off, after a catalog check under a SHARE UPDATE EXCLUSIVE lock, which blocks policy DDL and a second rebuild of the table, that refuses a RESTRICTIVE policy or a missing isolation policy before the first guard read. A BYPASSRLS maintenance role or a second owner role for rebuilds and migrations was rejected, because a second credential that skips every policy is what this layer exists to rule out. A per-table opt-out flag was rejected too: it hides the exemption in the schema instead of at the code path that needs it. A projection write keeps the tenant scope of the command, so WITH CHECK rejects a row for another tenant; only replays, rebuilds, boot seeds and global tables write in system scope, and an intended cross-tenant write goes through `ctx.systemDb` in an `r.systemScope()` feature. The event append scopes to the stream's tenant, because `writeAs` and `forTenant` legitimately append to another tenant's stream; its WITH CHECK therefore only confirms the stream tenant, and the authorization of a foreign stream stays with the dispatcher.

### 2026-10-23 The complexity guard covers .tsx

The complexity guard scans `.tsx` files with the same threshold of 15 and the same hard cap of 40 as `.ts`; `.test.tsx` files stay excluded like `.test.ts`. Conditional JSX (`cond && <X/>`, ternaries in markup) counts as a branch, because a screen with forty conditional slots is as hard to follow as a handler with forty `if`s. A component above the cap is split into a state hook, pure logic modules and `renderX(model)` functions with identical hook order and deps, not into new component layers. Existing `.tsx` hotspots between 15 and 40 were frozen in the baseline when the scan was extended; consumer repos freeze theirs with `--write-baseline` on the bump and split every function above 40.

### 2026-10-23 HandlerContext and JobContext use namespaces, without aliases

The flat members of `HandlerContext` are grouped by purpose: `db.outsideTransaction`, `events.*`, `dispatch.*`, `auth.*` and `obs.*`, with the matching subsets on `JobContext`. The flat names are gone instead of staying as deprecated aliases, because two names for one surface would double every denial proxy, every re-gate in `withHookEscapeHatchGrant` and every guard hint, and a codemod (`ctx-namespaces`) moves the call sites mechanically. `AppContext` stays flat: it is boot wiring, not a handler surface. The runtime handler object still doubles as the context of postSave, preDelete, postDelete and postQuery hooks and of `lifecycle-pipeline.ts`, so it keeps a flat `log` and `tracer` next to `obs`; splitting a hook context from the wiring follows in PR 3b. `outsideTransaction` is attached to the exposed `ctx.db` with `Object.defineProperty` (non-enumerable) and never through a wrapper or spread, because `TenantDb` object identity keys WeakMaps (rebinders, personal-data gates, write-denial reasons) that a copy would silently detach from. The phases that must not write get their own types, `ReservationContext` and `BeforeTransactionContext`, so a denied surface is a compile error instead of a runtime throw alone; the runtime denial stays as the second layer.

### 2026-10-24 HandlerContext drops the wiring; hooks get the HandlerContext

`HandlerContext` no longer inherits the flat `AppContext` wiring. What a handler may use of it is grouped into `ctx.services` (redis, cache sync, job runner, search, entity cache, secrets, files and the other injected services), `ctx.lifecycle` (`afterCommit`, `afterRollback`, `signal`, `runPreSave`) and `ctx.tenants` (`config`, `writeTarget`); the rest of the wiring (clock, registry-internal factories, the per-call notify factories) never reaches a handler. Keys of an app's `extraContext` that the framework does not know land in `ctx.services.extensions`: before, the boot spread them flat onto the context, where tsc could not see them and casts read them. `APP_CONTEXT_KEY_ROLES` classifies every `AppContext` key as service or wiring, so a new key is a compile error until someone decides. The hooks and the system hook definitions take the `HandlerContext` and not the `AppContext`, which removes the flat `log` and `tracer` the previous entry kept for them; there is no separate hook context type, because it would be the same type under a second name. `AppContext` declares `services?: never`, so passing a handler or job context to a function typed `AppContext` is a compile error instead of a silent read of members that are no longer there. `ctx.systemDb.outsideTransaction` was still reachable in `beforeTransaction` next to the denied `ctx.db.outsideTransaction`; it is now `undefined` there, redefined on the same object like the attach itself, because `TenantDb` identity keys the WeakMaps. For the same reason the member-resolution and pre-transaction contexts drop the notify factories from `ctx.services`, and member resolution drops `_fileProviderResolver`: a factory left next to a denied `notify` or `files` would rebuild it. The batch hooks (`postSaveBatch`, `postDeleteBatch`) used to get the boot context; they run on a handler context built per flush now. Keeping the old flat members as aliases was rejected for the reason of the entry above: two names for one surface double every denial.

### 2026-10-24 Public framework exports need a user

A name stays exported from a subpath of `@cosmicdrift/kumiko-framework` only if at least one consumer outside `packages/framework` imports it from that subpath: other Kumiko packages, samples, the framework docs, `kumiko-enterprise`, `kumiko-platform`, `kumiko-studio` and the seven apps. A `declare module` augmentation of an exported interface counts as a use. Names added since the last release stay public until a consumer could have adopted them. Names without a user lose the export: they stay as internal modules when framework code still uses them, and are deleted with their tests otherwise. A name declared in an entry file moves to an internal module next to it (`internals.ts` or `<entry>-internals.ts`) and the entry imports it from there. Exceptions that keep a name public without a scanned user: a type that consumers name in an inferred declaration (`AppConfig`, `TransitionGraph`, `PagedQueryHandlerDefinition`, `RedisSseBroker`, `EventDedup`, `IdempotencyGuard`; dropping it breaks declaration emit with TS2883), an interface that `declare module` augmentations target, and names that `bin/` imports (the inventory does not scan `bin/`). The public-exports baseline (`.kumiko-public-exports-baseline.json`) keeps the smaller surface, so a name only comes back through a breaking-aware refreeze, and a new public name needs a consumer or a recipe that shows it.

### 2026-10-26 Paddle replaces Dodo; Paddle.js is the one external CDN

`subscription-paddle` replaces `subscription-dodo`, which is removed without a deprecation period. Paddle acts as merchant of record like Dodo did, so the consumer-protection texts still come from `consumerProtection.providerTexts`, and it switches plans in the app through the subscriptions API like Dodo did. The environment (`sandbox` or `live`) is its own config key next to `billingLive`, as before. Paddle has no hosted checkout page: its Default Payment Link must point at a page of ours that runs Paddle.js. The feature serves that page itself at `/billing/paddle-checkout`, anonymous and rate limited, with its own header set instead of `securePageHeaders`, whose `script-src 'none'` would block it. Paddle.js from `https://cdn.paddle.com` is the one external script this framework allows, and only on this page: its CSP limits `script-src` to the SHA-256 of one static inline initializer plus that origin, and the page never reflects `_ptxn` or any other query value into script. Paddle.js is loaded without SRI because the script changes in place; the CSP limits script-src to the inline hash plus https://cdn.paddle.com. Success and cancel targets are same-origin paths only; anything else falls back to `/`. Paddle.js runs with a public client token and can open a checkout with any `customData` from the browser, so `custom_data.tenantId` proves nothing on its own. Every checkout and plan switch the server creates carries `tenantBinding`, an HMAC of the tenant id under a server-only key, and a webhook whose tenant id lacks a valid binding is dropped with a 200 after the signature check. Rotating that key leaves existing subscriptions unbound until they are re-bound, which is why it is a `backing:"secrets"` key with a documented rotation cost. A subscription still stays with the provider stored on it, and a plan switch never crosses providers, as in the entry of 2026-10-22. Self-hosting Paddle.js was rejected, because the script is only distributed from Paddle's CDN and changes in place; widening the CSP of every page was rejected, because only this page needs it.

### 2026-10-26 Inbound mail stores its content and never drops a mail silently

`inbound-mail-foundation` keeps the full text of a mail, capped at 32,000 characters, PII-encrypted in `inbound-message-received` (version 2). The original MIME goes to file storage as `bodyRef`, through the app's `storeBody` hook or, without one, under a deterministic key in the handler. Attachments become unattached fileRefs created by the system user, so only privileged roles read them until a consumer adopts them. Retention purges `bodyRef` with the message but never the attachments, because documents built from them outlive the mail. Attachment bytes travel in the in-process ingest payload; JSON over HTTP cannot carry them. A job triggered on the ingest write would serialize them, so jobs trigger on the events instead. A mail that fails validation or parsing goes into the store table `store_mail_quarantine` with a reason code, and the cursor moves on. An infrastructure error holds the cursor and only quarantines a message after three failed ticks in a row, so an outage does not empty the inbox into quarantine. The account turns `degraded` with a `lastError` code after three transient failures, on a new quarantine entry or when file storage is missing. It returns to `active` after a successful poll once the admin has acknowledged the quarantine. `lastError` holds codes mapped to locale keys, never provider texts, which can carry hosts or tokens. A disconnected mailbox is reconnected in place with the same accountId, so cursor, seen anchors and threads stay; connect rejects an address the tenant already has. OAuth reactivates a disconnected account of the same owner, because OAuth has no reconnect form. Mails imported before content storage get their content through `inbound-message-content-fetched` on the same stream while they are still on the server, within the backfill window, with a terminal `unavailable` state for mails that are gone. A connect, reconnect or switch to `active` wakes the sync at once through a per-instance event consumer (`startFrom: "now"`, woken by NOTIFY), so every worker sees it without a restart or a shorter poll interval; a wake that finds no credential stored yet does nothing and leaves the account to the next tick. For an IP-literal IMAP host the client connects without SNI (`tls.servername` unset), because Bun rejects the `servername: false` that imapflow sets; the certificate is still checked against the IP. Outgoing mail takes attachments by file reference (`attachmentFileIds`, at most 10 and 18 MB, resolved tenant-bound through file storage) because the caller already owns the file and a mail that silently lost an attachment would be worse than one that is not sent. One account's sync is bounded by concurrency 4, a skip of still-running syncs and a 10-minute deadline with an `AbortSignal`, because a single hanging mailbox must not stall all others. An `r.job` with `catchUp: true` gets its own consumer from the beginning of the event store and a deterministic job id, because the shared job-trigger consumer never replays events to a job added later. Sender authentication is only believed when the mailbox names its own server's authserv-id (`trustedAuthservId`): the first `Authentication-Results` header from the top with exactly that id counts, everything below it is ignored, and a result for another From domain than the mail's is dropped, so the `senderAuthentication` of a mail is null unless the account's own server vouched for its From domain and a sender cannot inject a pass.

### 2026-10-30 Work-queue rules are named list filters on the entity

A work-queue rule ("overdue", "mine") is a named list filter in `EntityDefinition.namedFilters`, not a filterable SQL-derived field or a metric. Such rules often need JS logic, for example an async lookup that returns an id list, and SQL could only reproduce it as a second implementation that drifts. The default list query resolves `namedFilter` and appends the conditions to `filters`, so the field-read and PII guards still apply, and a rule fails closed: a condition on a field the entity does not have is an internal error and never a dropped condition that widens the queue. A dashboard stat with `navigate` counts only from its own `params`, never from the dashboard filter, time range or record params, because the list it opens cannot carry them; the boot validator also requires the stat to use the target list's query and the same `namedFilter`, so tile and list cannot drift. No contradiction with an earlier entry found.

### 2026-10-30 Cleanup jobs use a maintenance trigger, not a shared cron string

`r.job` accepts `trigger: { maintenance: true }`: one run a day in the app's maintenance window, read from `KUMIKO_MAINTENANCE_WINDOW` (`HH:MM` UTC, default 03:00) when the job runner starts and registered as a BullMQ job scheduler with the pattern `<m> <h> * * *` in UTC. All housekeeping jobs of the framework and the bundled features moved to it, so an app that sleeps between requests is woken once a day for them instead of up to 24 times (the hourly upload and stale-run sweeps) or three times (03:00, 03:15, 03:30). A fixed cron string or a shared constant was rejected because the provisioner has to stagger the window per app, so that many sleeping apps on one host do not all start in the same minute; only a value read at runtime allows that. The window is a runner option and not read in `defineFeature`, so a changed value takes effect on the next boot through the existing scheduler upsert and orphan cleanup. `{ cron }` stays for jobs whose time matters (tenant destruction, workflow resume, app-specific schedules); each such time is one more wake-up. No contradiction with an earlier entry found.

### 2026-10-31 A failing search index holds only its own tenant

The search consumer keeps one shared cursor for all tenants, and a halt-on-poison there let one tenant's broken Meilisearch index stop indexing for everybody. Its batch handler now flushes tenant by tenant, replays a failed tenant batch op by op and holds only the failing ops through `BatchTurnControl.holdForRetry`; the dispatcher moves the cursor past them and keeps them in `pending_gaps`. That reuses the one place that already persists ids below the cursor in the same transaction, re-fetches them first in id order and never burns a visible id, so nothing is lost on restart and no schema change is needed. While a tenant backs off (1 to 60 seconds, in process memory) all of its ops are held, and held events come back with newer ones, so the last-op-wins collapse per entity keeps an old update from overwriting a newer one. For consumers with a batch handler, pending ids fill at most half of a dispatcher batch so held ids cannot starve newer events; when that cap leaves pending events out, newer events of their tenants are withheld as pending gaps, which keeps per-tenant order. Per-event consumers never hold, keep the full batch for pending ids and skip the extra tenant query. A tenant stuck for days leaves one gap range per run of its events between other tenants' events, so `maxPendingGapRanges` (default 2000, twice the warn threshold) bounds the cursor row: at the bound the batch consumer takes no new events and escalates like a poison event through `maxAttempts`, dead and rearm, which stalls every tenant but visibly and with the rearm-exhausted alert. A tenant-held marker that skips the stuck tenant's events in the fetch was rejected because it needs a `(tenant_id, id)` index on the events table, a migration in every app. A per-tenant consumer row or a dedicated retry table was rejected: the first needs a tenant filter in every fetch and a merge-back race with the shared cursor, the second needs a migration in every app and would copy decrypted search documents into Postgres. Holding never counts towards `maxAttempts`, like `errorPolicy.isTransientError`, because dead-lettering the shared consumer is exactly the stall for all tenants, and skipping automatically would silently drop documents from the index. The hold stays visible through `lastError`, `last_failed_event_id`, the failed-events counter and the pending-gaps gauge; after ten failed retries in a row the consumer logs an error and `lastError` names the stuck event and `skipPoisonEvent`. No contradiction with an earlier entry found, apart from narrowing the strict halt-on-poison order of the search consumer described in `event-dispatcher.ts`.

### 2026-10-31 Tenant destruction parks in `destroyHeld` while retention holds rows

When a data-retention spec holds rows with `blockDelete` inside `keepFor`, tenant destruction runs every stage up to `tenant-row` and then sets the status `destroyHeld` instead of writing the tombstone. The earlier stages leave the held rows alone, along with the files those rows reference (fileRef row and bytes) and the tenant's retention and compliance config. Everything else is deleted as usual, unreferenced files included. Parking counts as no stage attempt, so it produces no failure and no retry. The daily retention run deletes expired held rows together with their files. When a tenant has no held rows left, the same run moves it back to `destroying`, and the sweep writes the tombstone. Only an actual release writes an audit entry. The 60-minute pending window of the destruction stages is not used for this, because a hold of several years does not fit into it. `hasTenantDestructionWork` does not count parked tenants, so the per-minute sweep does not wake for them for years. `EXT_TENANT_DATA` hooks can declare `phase: "tenant-row"`. compliance-profiles and data-retention use it, so their config survives the hold and is deleted with the tombstone. No contradiction with an earlier entry found.

### 2026-10-31 Tenant inactivity reads activity from sessions into its own state

`tenant-inactivity` adds no write to the session refresh. Its daily job takes the newest `lastSeenAt` of the tenant's sessions in `store_user_sessions`, together with optional `activitySources` such as other apps of the same account, and folds it into `lastActivityAt` in its own state table. The fold only ever raises the value, so the session cleanup that deletes old sessions cannot reset it. A write in the session refresh was rejected because it would put a second write on the hottest auth path for a value needed once a day. When an activity source fails, the job sends no mail and files no deletion request for that tenant in that run, so an outage of a sibling app cannot get an active account deleted. No contradiction with an earlier entry found.

### 2026-10-30 Full-text search goes through the SearchAdapter, long fields are chunked

Full-text search over long personal fields uses the SearchAdapter (Meilisearch), not Postgres full-text search: personal fields are encrypted at rest, and a tsvector would need their plaintext in the database. `createLongTextField` therefore accepts `find: "fuzzy"`, which puts the decrypted value into the search document only, and never an SQL `ILIKE`. Meilisearch indexes at most 65,535 word positions per attribute, so string fields over 8,000 characters are split into pieces of at most 8,000 characters, cut at whitespace with about 200 characters of overlap; nothing is cut off silently. The first piece keeps the document id the entity always had, further pieces are `<id>_c<n>`, and `distinctAttribute: "_entityId"` makes an entity match once. A change of the document format (`SEARCH_DOCUMENT_FORMAT_VERSION`) or of an entity's search fields reindexes that entity once at boot in the background, guarded by a Postgres advisory lock so that several pods run it once, with the completion marker written only after a clean run. No contradiction with an earlier entry found.

### 2026-11-01 Public handlers admit every signed-in caller through `anySignedIn`

A public handler (roles include `anonymous`) used to list the signed-in roles it also accepts, so a visitor who was signed in with an app-specific role such as `Hausmeister` got a 403 from the waitlist, the contact form or a managed page, because the browser sends the session cookie along and the session no longer carries `anonymous`. `RoleAccessRule` now takes `anySignedIn: true`: `hasAccess` and `isUiAccessGranted` let every non-anonymous caller through such a rule, and boot rejects the flag on a rule without `anonymous` (that would be `openToAll` without a reason) and any value other than `true`. The bundled public intake and public read handlers set it; the anonymous-only auth handlers (signup, password reset, invite, MFA preauth) keep `roles: ["anonymous"]`, because a signed-in caller there is a mistake. Making `anonymous` match every caller was rejected because it would widen exactly those handlers, and a wildcard role string was rejected because every role validator and the feature AST would have to learn that one string is not a role. The contact website client additionally sends without credentials, so it always arrives as anonymous. No contradiction with an earlier entry found.

### 2026-11-01 Webhook events are released per token scope and only with a public contract

`PatScopeDef.events` lists the webhook events a scope exposes by exact name, and holding the scope's read level is enough to subscribe. An event is releasable only with a public contract: `r.defineWebhookEvent({ name, description, payload, version })` for app and bundle events, or the contract the registry derives for an entity event (`ticket.created`) from the entity schema, without personal fields and without the CRUD `excludedFields`. An internal `r.defineEvent` event has no contract and is never released; the boot check of `personal-access-tokens` rejects a scope that lists one and names the fix. Delivery (signing, retries, envelope, delivery id) stays in the consuming app; the framework only offers `parseWebhookPayload`, which validates against the contract and strips unknown keys, so personal data cannot leave through an extra property. Releasing internal events with a field allow-list was rejected because the payload of an internal event may change at any time and the allow-list would then drift unnoticed. A shape derived from the stored event payload was rejected for declared events because their contract must stay stable when the internal event changes. The registrar takes one options object, not positional arguments. Derived entity contracts are an opt-in per entity (`webhookEvents: true`), secure by default: bundle system entities such as `config-value` (its `value` can hold an encrypted secret blob), `tenant-secret` or `user` must never become releasable through a token scope, and the code has no marker that tells a bundle entity from an app entity, so no bundle entity sets the flag. The field exclusions stay as a second layer. Deriving for every entity and excluding bundle entities by a list was rejected, because a new bundle entity would be released until someone remembered the list. No contradiction with an earlier entry found.

### 2026-11-02 Content previews go through a renderer registry keyed by preview target

Every content editor (mail and PDF templates, layouts, managed pages, text blocks, collection entries) uses the same editor shell with an edit and a preview mode. The shell moves from `document-designer` into `renderer` as a presentational component, because `bundled-features` must not import `document-designer` and the shell only depends on `renderer` anyway. Edit formats stay `plain` and `document`, as the editor round settled (`docs/archive/plans/editor-document-round.md`). Previews get their own registry next to `contentEditors`: `contentPreviews` maps a `PreviewTarget` (`pdf`, `mail`, `web`, `text`) to a renderer, with the same last-wins merge, and `text` (the former `ContentPreview` toggle) is the fallback. The target follows from the template kind through a complete record over the editable kinds (every `TemplateKind` except the retired `notification` and `image-snapshot`, which takes ready HTML and has no editor), so a new kind fails the typecheck until it gets a target or is excluded on purpose. Managed pages are not a template kind and hand `web` to the shell directly (renderer and query belong to `template-resolver`); collection entries are stored as `snippet` and get `text`. Each renderer calls its own server path under its own access rule: `document-designer` registers `mail` and `pdf` on `template-resolver:query:preview` and `previewPdf`, `template-resolver` registers `web` on one body preview query for the unsaved state (`template-resolver:query:body-preview`, uncached; access is the union of the roles that may write a body: SystemAdmin plus the `tenantEditable` roles for text blocks, and TenantAdmin for pages), which renders through the same markdown core and document sanitizer as the managed-pages and legal-pages visitor paths. `managed-pages` has neither its own query nor its own renderer, because an app can mount legal-pages without managed-pages and the legal text preview must not depend on it; `textBlocksClient` and `managedPagesClient` both mount the same renderer so an app with only one of them still previews. Collection entries in `document` format, which tenant members may edit, do not call the server: the client fills the example values and shows the HTML in the sandboxed `HtmlMailFrame`. Extending `template-resolver:query:preview` to every target was rejected because it is admin-only while collections are open to tenant members and user content lives in its own table. Letting every feature render its own preview inside its own screen was rejected because it duplicates the shell logic and is not declarative. A `previewTarget` field on content collections is left out until a consumer inserts snippets into mails. No contradiction with an earlier entry found.

### 2026-11-02 System tenant read policy only on classified tables

**The system tenant read policy exists only on tables classified `systemRowsReadable`.** `kumiko_system_tenant_read` lets a tenant session read rows with `tenant_id = SYSTEM_TENANT_ID`. It used to sit on every table with a `tenant_id` column, and since users, MFA, API tokens, sessions and tenant secrets moved to the system tenant, the second RLS layer let any tenant session read them past a missing TenantDb filter. The policy is now a positive classification: an entity (or `defineUnmanagedTable` input) sets `systemRowsReadable: true`, an entity targeted by `r.referenceData` is classified implicitly (its rows live on the system tenant by definition), and a table without it gets only `kumiko_tenant_isolation`. Only shared data that a tenant read must see (templates, config defaults, custom-field definitions, reference catalogs) is marked; an auth, credential, secret, session or PII table is never marked, and its system tenant rows stay reachable through the system scope. The boot check expects exactly the classified set, so a system read policy on an unmarked table is a finding as well as a missing one on a marked table. This is not the per-table opt-out flag rejected above: that flag exempts a table from isolation, while this marker widens read access for one named table and the default is closed. A deny list of credential tables was rejected, because a new table on the system tenant would be readable until someone remembered the list. This supersedes the policy list of the row level security entry above ("the policies `kumiko_tenant_isolation` and `kumiko_system_tenant_read`" on every tenant table): isolation stays on every table, the system read policy narrows to the marked ones.

### 2026-11-03 Parent-ref gate resolves global hosts in the system scope, the gated statement stays tenant-scoped

**A join row on a `tenancy: "global"` host is gated by host ids resolved in a separate system-scope statement.** Row level security sets one scope per statement, and since the system tenant read policy was narrowed a tenant-scoped statement no longer sees the system tenant rows a global host lives on, so the parent-ref `EXISTS` hid every note, tag or folder assignment on such a host. The list, detail and row-readable checks of the event-store executor first run the same host check (host tenant, soft delete, the host's `access.read`) in the system scope, restricted to the caller's own join rows by an explicit `tenant_id = session tenant` filter, and pass only the host ids into the gated statement (`ParentVisibilityOption.globalHostIds`); a path without that step leaves the global host arm out and denies. Running the whole gated statement in the system scope was rejected: its tenant filter is `tenant_id IN (session tenant, system tenant)`, so it would expose the join table's system tenant rows (for example notes a SystemAdmin wrote in the system tenant) that row level security hides from tenant sessions. Marking global host tables `systemRowsReadable` was rejected because they hold PII and credentials. This refines the 2026-11-02 entry on the system tenant read policy, it does not reopen it.

### 2026-11-03 An agent tool call reads global catalogs through a tenant-mode db

**Inside an agent tool call, a system-scope handler runs only if it is the convention list or detail query of a `tenancy: "global"` entity, and then without the system scope.** Since the agent scope refused every `r.systemScope()` handler, an assistant could no longer read a global catalog such as the campaign channels. Such a query is now resolved as if its feature were not system-scoped: no `ctx.systemDb`, a tenant-mode `ctx.db` and no identity-switch grant, so the read sees the caller's tenant plus the system tenant rows of the global table and nothing of other tenants. A query that declares an `escapeHatch` is not covered, so no identity switch runs on behalf of the LLM, and the rate limit keeps the system-scope default. Writes, entity-less system queries and queries on entities without `tenancy: "global"` still throw `agent.tool_not_allowed`. Widening this to every `systemStream` entity was rejected, because a system-stream entity without the global classification can hold per-tenant data that only the system scope is meant to read. Running the query in the system scope with a filter was rejected, because one forgotten filter would read across tenants on behalf of the LLM. This narrows the agent-scope refusal, it does not reopen the cross-tenant protection.

### 2026-11-04 Work-queue lists stay declarative: named filters carry sort and empty state, the dashboard grid has twelve columns

**A list that is a work queue (a "to do" select with hit counts, urgency order while a filter is on, an empty state that says the queue is done) is configured on the screen, not written as a custom screen.** `namedFilterFacet` presents the existing `namedFilters` as one single-choice select, `showCounts` reuses the facet-count requests (the list's own payload per offered filter, reduced to `limit: 1, totalCount: true`; the `select` variant adds one without a filter for "all"), `NamedListFilterRef.sort` wins over `defaultSort` while that filter is active and the URL carries no sort, and `NamedListFilterRef.emptyState` replaces the generic "no matches" text with a sentence and a reset button, only when neither a search term nor another facet narrows the list as well. ### 2026-11-04 Row tone is a stripe, not a fill; list summaries come from a query
